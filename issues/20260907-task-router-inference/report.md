# vuoi タスクルーターが弱い — 現状と変更方針

調査日: 2026-09-07 / 対象: `chevuoi`（main = 7843d6e） / Trello: https://trello.com/c/BMteMbAP/2014

## 背景・問い

カード→ワークフローのルーター（`ClaudeWorkflowRouter` / `SelectWorkflowUsecase`）について、「タスクルーターが弱くて、カードに明示しないとワークフローを決定できない。もう少し推論してほしい」という問題提起があった。

ルーターはカード1枚につき必ず1回走る入口の判断であり、誤ると worktree 作成・`claude` 実行・PR 作成まで実行1本ぶんを無駄にする。仕様上も「改善 ROI が最も高い」と位置づけられている（`docs/spec/cli.md`）。

問いは次の3つ。

1. 「弱い」の実体は何か。棄権が多いのか、誤選択が多いのか、その他か
2. 原因はどこにあるか（モデルの能力 / プロンプト / 入力 / 判断基準 / 仕様と実装の乖離）
3. どう変えるべきか

**手順**

集計は `analyze_router_log.sh` にまとめ、結果を `router-log-summary.txt` に保存した（再実行可能）。集計項目は、層別の発火件数・棄権の内訳・選択先の分布・理由文が自己申告を根拠にしている件数・同一タイトルで判定が割れたカード・`claude` 実行時のモデル指定。

**前提・限界**

- ログに残るのはタイトル・選択・確信度・理由のみで、カード本文は残らない。したがって「本文に何が書かれていたか」は理由文からの間接的な確認にとどまる

- LLM を伴う再実行（`vuoi workflow select` による再現）は行っていない（コストとレート制限のため）

## 結果（事実）

### F1. 棄権はほぼ起きていない

LLM ルーティング 106 件のうち、棄権（`workflow=None` または `confidence=low`）は 2 件のみ。その 2 件はいずれも推論の結果ではなく、`claude` の実行失敗だった。

```
2026-09-07 10:42:12 ルーティング(LLM): vuoi トリアージ機能の設計 -> None (confidence=low)
  ルーター実行失敗: You've reached your Fable limit. ...
2026-09-07 10:42:13 ルーティング(LLM): 未来リサーチ 今までの実験まとめ -> None (confidence=low)
  ルーター実行失敗: You've reached your Fable limit. ...
```

推論の結果としての棄権は **0 件**。なお `ProcessCardUsecase` の needs_human コメント（`process_card_usecase.py:145`）は `card.add_comment` がログ出力を伴わないためログには元から現れない。棄権が 0 件であることは上の 106 件の判定行から直接わかる。

### F2. 選択先は `dev` に偏っている

| 選択先 | 件数 | 割合 |
|---|---:|---:|
| `dev` | 61 | 58% |
| `doc` | 21 | 20% |
| `research` | 12 | 11% |
| `task` | 4 | 4% |
| `academic_writing` | 4 | 4% |
| `design` | 2 | 2% |
| 棄権 | 2 | 2% |

### F3. 選択理由の 1 割強がカード本文の自己申告を根拠にしている

106 件中 **12 件（11%）** の理由文が、カードが自分の種別を名乗っていることを直接の根拠として挙げている。種別名は出さないが「これを実装して」のように作業を明示的に指定している例まで含めると 15 件（14%）。

- 「『実装タスク』と明記され、削除ボタンの活性条件…」
- 「カード本文が『調査タスクです』…」
- 「カード自身が『レポートタスク』と明記し…」
- 「カードは『実装はしない設計検討レポーティングタスク』と明記し…」
- 「カード冒頭に『ドキュメント編集タスクです』と明記され…」
- 「カード本文に『設計タスクです』『まず仕様を考えてみてください』と…」

本カード自身も、本文が「検討タスク」で始まっている。

なお `router-log-summary.txt` の「20 / 106」は集計スクリプトの粗い grep（`明記|明示|冒頭に「|カード自身が|カード本文に「`）の生の値で、自己申告ではないものを 4 件拾っている（候補側の `when_to_use` が「他 PR のレビュー」を明示していることを根拠にしたもの 2 件、「lint ルールの明示」1 件、「修正対象と根拠行が明示されている」1 件）。上の 12 件 / 15 件は、その 20 件を目視で選り分けた値。

### F4. 第1層（決定的マーカー）の発火は 0 件

`_by_marker`（`select_workflow_usecase.py:60`）はタイトルから `\[([a-z0-9][a-z0-9_.-]*)\]` を拾い `meta.intents` と突き合わせる。ユーザー定義ワークフローの intent は `card.dev` / `card.research` / `card.doc` / `card.design` / `card.task` / `card.merge` / `card.academic_writing` であり、効かせるにはタイトルに `[card.research]` と正確に書く必要がある（`[research]` では一致しない）。

実運用 106 件中、第1層の発火は **0 件**（ログの「ルーティング(決定的)」が 0 行）。

### F5. ルーターはモデル未指定のまま Claude Code の既定モデルで動いている

`config.toml` / `config.linux.toml` のどちらにも `[router]` セクションが無く、`RouterConfig.model` は `None`。ログ上の `claude` 実行 438 件すべてが `model=None`（＝ `--model` を渡さない＝ Claude Code の既定モデル）。仕様は `[router]` で軽量モデルを指定することを推奨しており（`docs/spec/workflow-engine.md`）、設計文書は指定なしの既定モデルを「重いモデル」と記述している（`docs/design/20260829-runner-model-and-light-router/design.md`）。F1 の失敗メッセージがレート制限であることも、軽量モデルではないことと整合する。ただしログに残るのは `model=None` だけで、実際に解決されたモデル名は記録されていない。

### F6. ルーターに渡る入力はタイトルと本文のみ

`build_prompt`（`claude_workflow_router.py:82`）がプロンプトに載せるのは、カードの `name` / `desc`（空なら「（本文なし）」）と、各候補の `name` / `summary` / `when_to_use` だけ。次は渡らない。

- プロジェクトタグと対象リポジトリのパス（`SelectWorkflowUsecase.execute` は `cwd=project.repo_path` を受け取っているが、プロンプトには載らない）
- カードのコメント（`Card.fetch_comments` は存在し、`ProcessCardUsecase.build_message` は使っているが、ルーターは使わない）
- Trello のラベル（`Card` にラベルの概念自体がない）
- リポジトリの中身。`allowed_tools=("Read", "Grep", "Glob")` と `cwd` は渡っているが、**プロンプトにリポジトリを見てよいとも見ろとも書かれていない**

### F7. 現在の判断ルールは `ed1574b` で逆症状を潰した結果

プロンプトの「判断ルール」節は5行。うち後半3行はコミット `ed1574b`（2026-08-29「Googleドキュメントの取得不確実性がタスク選択の不確実性として評価されてる」）で入った（3行目は既存1行の書き換え、4〜5行目が新規追加）。

```
- 確信度は「カードの記述がどの候補に当てはまるか」の明確さだけで決める。用途が明確に読み取れるときは "high" とする
- 作業の実行可能性（外部資料や Google Docs 等の取得可否、アクセス権、作業の難易度・規模）は確信度に反映しない。それらは後続のワークフローが判断する
- 変更対象がコードかドキュメントかの別も、候補の when_to_use がその区別を求めていない限り確信度に反映しない
```

当時の症状は逆で、`dev` と判定できているのに実行可能性の不安から `low` に落ちて `needs_human` が頻発していた。変更前の文言は「確信度は、カードの記述から用途が明確に読み取れるときだけ "high" とする」。

同コミットの自己レビューには、次が「別途整理が必要」として残されている。

> `docs/spec/triage.md` は確信度の実質を「受け入れ基準を書き下せたか / 対象ファイルを特定できたか」としているが、現行ルーターは名前選択のみで受け入れ基準を抽出していない。

### F8. 出力と棄権の判定は LLM の自己申告に依存している

出力は JSON 1個（`{"workflow", "confidence": "high"|"low", "reason"}`）。ホスト側の検証は「名前が候補に実在するか」と「`confidence == "high"` か」の2点のみで、確信度はそのまま信じている。

`_extract_json` の抽出は `re.search(r"\{.*\}", text, re.DOTALL)`（貪欲マッチ）。JSON の後ろに `}` を含む文が付くと解析に失敗し、棄権になる。

### F9. 仕様と実装の乖離（ルーター関連）

`docs/spec/triage.md` のうち未実装のもの。

- 第1層のタグ規則（`spike` → investigate、`adr` → design、`typo`/`bump`/`deps` で始まるタイトル → trivial）。ラベルの取得経路自体がない
- **「本文が空 → `needs_human`」**。現状は「（本文なし）」としてそのまま LLM に投げる
- 第2層が返すべき「対象ファイルの候補」「受け入れ基準の一覧」
- 第3層の「受け入れ基準が1件も抽出できなかった場合は棄権」
- 経路の途中での reroute（1ランにつき1回まで）

### F10. 精度を測る手段がない／判定の不安定さが1件観測された

- 判定は `logger.info` の1行テキストとしてしか残らず、カード ID も後段の終端状態も紐づいていない
- `docs/spec/cli.md` の「経路 × 終端状態の混同行列」に相当する集計は CLI に未実装（`vuoi workflow` は `list` / `run` / `select` のみ）
- 同一タイトルで判定が割れた例が1件（カード ID が残らないため、厳密に同一カードだとは確認できない）: 「texts ループエンジニアリング記事構成作成」→ `academic_writing`（09-05 11:55）→ `academic_writing`（09-05 18:37）→ **`doc`**（09-06 07:24）

## 考察と結論

### 結論: 「弱い」の実体は、棄権の多さではなく明示への依存

F1 と F2 を合わせると、現状のルーターは「決められないときに止まる」のではなく「**明示がなければ `dev` と言い切る**」挙動である。棄権パスは仕様どおり実装されているのに、実質的に一度も発火していない。したがって誤ルーティングは棄権として表面化せず、間違ったワークフローが最後まで完走する形でしか現れない（F10 により、それも観測できない）。

F3 の「理由の1割強が自己申告を根拠にしている」は、ユーザーが本文に「調査タスクです」と書く運用が、この挙動への適応として定着していることを示す。棄権時のコメントが「カードの本文に作業の種類を書き足してください」と指示している（`process_card_usecase.py:145`）ことも、明示依存を運用として固定する方向に働いている。

### 原因は4つ。いずれもモデルの能力ではない

F5 より、ルーターは軽量モデルではなく Claude Code の既定モデル（設計文書いわく「重いモデル」）で動いている。モデルを絞ったせいでこの挙動になっているわけではないので、原因は入力・プロンプト・判断基準の側にある。なお本調査ではモデルを変えた比較実験は行っていないため、「別のモデルなら改善しない」ことまでは示していない。

**原因1: プロンプトが推論を禁じる方向に効いている（F7）**

`ed1574b` の修正自体は正しかった（実行可能性を確信度に混ぜるのは明確な誤り）。ただし副作用として「確信度の根拠は**カードの記述の明確さだけ**」という縛りが残った。カードの記述が明確 ≒ カードが自分の種別を名乗っている、なので、**作業内容から種別を推論することが確信度の根拠として認められていない**。これが「明示しないと決まらない」の直接の原因である。

**原因2: 入力が薄い（F6）**

判断材料がカード本文しかなければ、本文の自己申告に頼るのは必然である。特に、読み取りツールと `cwd` を渡しながらプロンプトで一言も触れていないため、権限を持ちながら実質はテキスト分類になっている点は、費用をかけて効果を捨てている状態と言える。

**原因3: 判断が抽象的すぎる（F7・F9）**

仕様は確信度の実質を「受け入れ基準を書き下せたか / 対象ファイルを特定できたか」という具体的な作業に置いていたが、実装は「種別名を1つ選ぶ」という抽象1発に圧縮されている。仕様が用意していた**推論の足場**と**検証可能な棄権条件**が両方とも失われている。

**原因4: 第1層が実質死んでいる（F4）**

`[card.research]` とフル intent を書かないと効かない。仕様が主張する「人間がラベルを1つ付ける行為自体がルーティング決定。最も安く最も正確な判断手段」は、実装されているのに使われていない。これは「明示しないと決まらない」の裏面、すなわち**明示したいときの明示コストが高すぎる**という問題である。

### 変更方針

芯は「**明示を要求するのをやめ、推論の材料と判断軸を与える**」。ただし次の2つは仕様の根幹なので崩さない。

- 棄権パスは外さない（「必ずどれかを選ばされるルーターは必ず間違える」）
- LLM が返すのは候補名1つだけ。決定は名前の実在確認を通じてホストが行う（非決定性を一点に封じ込める）

**方針1: 第1層（決定的）を実用化する — LLM 不使用**

- マーカーの短縮形を許す。intent の末尾セグメント（`card.research` → `research`）とワークフロー名にもマッチさせる。曖昧さが出る場合は既存の `check_intent_conflicts` と同じ流儀で「勝たせずに無効化」する
- Trello のラベルを第1層の入力にする。`Card` にラベルを足し、ラベル名 → intent の対応を設定に置く
- 効果: 明示のコストが「本文に日本語で種別を書く」から「ラベル1つ / `[research]`」に下がり、その明示は LLM を通らないので確実に効く

**方針2: プロンプトの判断ルールを「推論してよい」に書き換える**

- 削る: 「確信度は『カードの記述がどの候補に当てはまるか』の明確さだけで決める」
- 置き換える: 「カードが自分の種別を名乗っていなくても、記述された作業内容から成果物の形が一意に決まるなら `high` とする」
- 残す: 実行可能性を確信度に混ぜないという `ed1574b` の2行（正しい修正なので再発させない）
- 足す: 判断の軸を「種別は何か」から「**この作業の成果物は何か**」へ移す。(1) コミットできる差分が成果物か、作業と報告だけか (2) 差分の中身はコードか文書か (3) 文書なら新規の調査報告か / 既存文書の追随か / 実装前の設計か
- 持ち込まない: この決定木をコードや設定に持たせない。ワークフローを増やしてもルーター側を触らずに済むという現在の設計上の利点（`docs/spec/workflow-engine.md`）を守り、個々の分岐は各ワークフローの `when_to_use` に委ねる

**方針3: 入力を厚くする**

- プロジェクトタグと対象リポジトリのパスをプロンプトに載せる
- カードのコメントを載せる（差し戻し2周目で作業の性質が変わることがある）
- 「必要なら Read / Grep / Glob で対象リポジトリを確認してよい（数回まで）」と明記する。`cwd` と権限は既に渡っているので追記だけで足りる
- 副作用としてコストとレイテンシが増える。`[router] model` を明示的に固定する（現在未設定なので、効果測定の前提としてまずここを揃える）

**方針4: 出力を厚くし、棄権を検証可能な条件にする**

- JSON に `deliverable`（この作業の成果物を1行で）と `targets`（対象ファイル・ディレクトリの候補、0件可）を足す
- **`deliverable` を書けなければ棄権**とする。2値の自己申告より、ホスト側で存在を検証できる条件のほうが安定し、「フロー制御に LLM を使わない」原則にも合う
- `confidence` は残すが、単独の門番からは降格させる
- 後方互換: 追加フィールドが無い出力は従来どおり `confidence` で判定する

**方針5: 精度を測れるようにする**

- ルーターの判断を構造化して残す（JSONL）。カード ID / タイトル / 選択 / 確信度 / 理由 / 発火した層、および後段の終端状態（PR / 変更なし / blocked / needs_human）
- `vuoi workflow select` にバッチ入力を足し、過去カードで回帰評価できるようにする。既存 106 件はログからタイトルが復元でき、正解ラベルは実際に人間が受け入れた結果から作れる
- `docs/spec/cli.md` の「経路 × 終端状態の混同行列」を最小形で実装する

### リスク

- 推論を強めるだけだと、棄権率 0% のまま誤ルーティングが増える。方針4 を必ずセットにする
- リポジトリ参照を許すとコストがカード1枚ごとに乗る。上限を切り、測ってから広げる
- `ed1574b` で潰した挙動が再発しうる。該当ルールとそのプロンプトテスト（`test_prompt_excludes_feasibility_from_confidence`）は残す
