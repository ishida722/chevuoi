# 対話中の Claude から vuoi のワークフローを呼び出す — 調査と方針

調査日: 2026-11-18 / 対象: `chevuoi`（main = 38eb92d）、`~/.config/vuoi`（ワークフロー 7 本）

## 背景・問い

vuoi のワークフロー（dev / research / design / doc など）は、Trello のカードを起点に「取得 → プロジェクト特定 → ワークフロー選択 → worktree → 実行 → PR → カード更新」と一気通貫で流れる。リモートのマシンで動いているこの運用は今後も続ける。

問題は、手元で Claude と対話しながら開発を始めたときに、このワークフローを使えないことである。対話で方針を決め、「よし、ここから開発にする」という段階で、次のことをしたい。

1. 対話中の Claude がワークフロー（例: dev）を起動する
2. 対話で決めた方針などのコンテクストを適切に渡す
3. 実行結果（PR・ブランチ・要約・未解決事項）を対話側で受け取り、続きを進める

問いは次の 3 つ。

- 現状のどこが「流れの固定」になっているか
- 何を切り出せば、カードを経由せずにワークフローを呼べるか
- 呼び出し口を MCP にするか、CLI とスキルにするか

## 調査方法

- カード処理の本体 `application/usecases/process_card_usecase.py`、単発実行の `run_workflow_usecase.py` と `interfaces/cli/commands/workflow.py`、手入力カード `interfaces/cli/adhoc_card.py` を読んだ
- グラフ実行のポート `domain/ports/graph_executor.py` と SDK `vuoi_sdk/__init__.py`（`WorkflowContext` / `ProjectInfo` / `Runner`）を読んだ
- dev ワークフロー（`~/.config/vuoi/workflows/dev/`）のノード構成と入力の受け取り方を確認した
- 実行ログで 1 件あたりの所要時間を確認した（dev 1 件: 10:35 → 10:49、約 13 分）

## 分かったこと

### 1. ワークフロー本体はすでにカードから独立している

- ワークフローの入力は、文字列の message 1 つである。カードからは `build_message()` がタイトル・本文・レビューコメントを 1 つの文字列にまとめて渡している
- ワークフローが参照する実行環境は、`WorkflowContext` の `workdir`・`project`（`ProjectInfo`: 名前・パス・テストコマンド）・`has_changes()`・`propose()` だけで、Trello は出てこない
- 結果は `ExecutionResult`（`summary` / `blocked` / `proposals` / 最終 state）で返る

つまり「ワークフローを呼んで結果を受け取る」部分は、すでに部品として成り立っている。

### 2. 固定されているのは、その前後をつなぐ `ProcessCardUsecase`

`ProcessCardUsecase.execute(card)` が、次の処理を 1 本の手続きとして持っている。

| 段階 | 内容 | カードへの依存 |
|---|---|---|
| 入口 | `card.claim()` | あり |
| プロジェクト特定 | タイトル先頭のタグ → `config.toml` の対応表 | あり（タイトル） |
| ワークフロー選択 | ルーター（LLM）が名前を 1 つ選ぶ | あり（タイトル・本文） |
| 作業場所 | `worktrees.create(project, card)`（最新の main から、ブランチ名はカード ID 由来） | あり（ID） |
| 実行 | `executor.execute(workflow, message, workdir, project, has_changes)` | なし |
| 終端処理 | blocked / コメント報告 / 変更なし / PR 作成 を決定的に判定 | 一部（PR 本文に Trello URL） |
| 出口 | 起票・カードへのコメント・In review へ移動 | あり |

真ん中の「作業場所 → 実行 → 終端処理」はカードにほとんど依存していない。それでも入口と出口と同じ手続きに埋め込まれているため、カードなしでは呼べない。これが「取得から完了までが固定されている」の実体である。

### 3. 既存の単発実行（`vuoi workflow run`）では代わりにならない

`vuoi workflow run <name> "message"` はカードなしでワークフローを呼べるが、次のものを渡さない。

- **worktree**: カレントディレクトリでそのまま実行する（手元の作業ツリーを直接書き換える）
- **プロジェクト情報**: `project=None` のため、テストコマンドがない。dev はテストゲートで blocked になる
- **変更の有無の判定**: `has_changes` を渡さないため、ワークフローは常に「変更あり」として扱う
- **終端処理**: PR を作らず、結果は標準出力にテキストで出るだけ。機械的に読める形式ではない

もともとワークフローの動作確認用のコマンドであり、対話からの呼び出し口としては足りない。

### 4. 対話から呼ぶときに要るもの

カード起点と対話起点の違いを並べると、必要な口が見える。

| 項目 | カード起点（現状） | 対話起点（欲しいもの） |
|---|---|---|
| コンテクスト | カードのタイトル・本文・コメント | 対話で決めた方針（目的・決定事項・受け入れ条件・触らない範囲） |
| プロジェクト | タイトルのタグ | 今いるリポジトリ（パスで特定） |
| ワークフロー | ルーターが選ぶ | Claude（またはユーザー）が名指しする |
| 起点のブランチ | 常に最新の main | 既定は main。対話中の作業の続きなら現在の HEAD も選べる |
| 結果の返し先 | カードへのコメント | 呼び出し元が読める構造化データ（JSON） |
| PR | 必ず作る（outcome = pr のとき） | 作るか、ブランチを残すだけにするかを選べる |
| 副次タスク | Inbox へ起票 | 結果に含めて返し、起票するかは対話で決める |

## MCP にするか、CLI とスキルにするか

**最初は CLI とスキルで作り、MCP は後から薄くかぶせる。** 理由は次のとおり。

- **実行が長い。** dev は 1 件で十数分かかる。MCP のツール呼び出しは応答を待つ作りなので、タイムアウトの心配がある。非同期にすると「開始」「状態確認」「結果取得」の 3 ツールが要り、Claude に状態を何度も確認させることになる
- **Claude Code は長いコマンドをすでに扱える。** Bash をバックグラウンドで実行すると、終了したときに Claude が再度呼び出される。「起動して別の作業をし、終わったら結果を読む」流れが追加の仕組みなしで成り立つ
- **コンテクストはファイルで渡すのが確実。** 対話で決めた方針は長くなる。ブリーフを Markdown ファイルに書いて渡せば、あとから人間も読めて、再実行にも使える
- **結果もファイルで受け取れる。** JSON を出力すれば、Claude は読んでそのまま続きを判断できる

MCP が必要になるのは、Bash を使えないクライアント（Claude Desktop など）から呼びたいとき、または実行中のランの一覧や状態を常にツールとして見せたいときである。そのときは同じユースケースと、永続化したランの状態を使う薄い MCP サーバーを足す。中身を作り直す必要はない。

## 方針（2026-11-19 改訂: 最小構成にする）

worktree と PR を選べるようにする案は、組み合わせごとの例外処理（未コミットの扱い、main での PR、起点のブランチなど）が増えて仕様が複雑になった。そこで、**まずは今の作業ツリーでワークフローを起動して結果を受け取るだけ**の最小構成にする。worktree の作成、コミット、プッシュ、PR 作成は vuoi では行わず、必要なら呼び出し元（対話側の Claude と人間）が行う。

この構成なら `ProcessCardUsecase` に手を入れる必要がなく、リモートで動いている Trello の運用に影響しない。

### やること

対話からの呼び出し専用の新しいコマンド `vuoi exec`（名前は仮）を作る。既存の `vuoi workflow run`（ワークフローの動作確認用）はそのまま残す。

```bash
vuoi exec dev \
  --brief brief.md        # 対話で決めた方針をファイルで渡す
  --json result.json      # 結果を JSON で書き出す
```

足りていなかった 4 点（「分かったこと」の 3）のうち、worktree と終端処理を除いた 2 点を埋め、入出力を整える。

1. **プロジェクト情報を渡す。** カレントディレクトリの git リポジトリのルートを求め、`config.toml` の `[projects]` に同じパスがあれば、そのテストコマンドを `ProjectInfo` として渡す。無ければ `--test-command`（複数指定可）で渡す。どちらも無ければ現状どおり `project=None` で実行する（dev はテストゲートで blocked になる。その旨を結果に載せる）
   - リポジトリのルートで照合するので、呼び出し元が別の worktree の中にいても同じプロジェクトとして扱える（パスの照合方法は実装時に確認する）
2. **変更の有無の判定を渡す。** `has_changes` は「作業ツリーに差分がある（`git status --porcelain` が空でない）」とする。開始前から未コミットの変更がある場合は常に「変更あり」になるが、影響は dev の差分ゲートがレビューを飛ばさなくなる（レビューが 1 回余分に走る）だけなので許容する（2026-11-19 決定）。問題になれば、開始時点との差分で判定する方式に変える
3. **ブリーフをファイルで受け取る。** `--brief` で渡したファイルの中身をそのまま message にする
4. **結果を JSON で返す。** `--json` で指定したファイルに書き出す。中身は次のとおり
   - `status`: `done` / `blocked` / `error`
   - `workflow`、`workdir`
   - `summary`（`ExecutionResult.summary`）、`blocked`（理由）、`output`
   - `changed_files`: 実行後の `git status --porcelain` の結果
   - `proposals`: 副次タスクの申告（起票はしない）

終了コードは、`done` なら 0、`blocked` なら 2、ワークフローが存在しない・ロードに失敗したなどのエラーなら 1 とする（既存の `workflow run` の 1 と揃える）。

### やらないこと（今回の範囲外）

- worktree の作成、コミット、プッシュ、PR 作成
- ルーターによるワークフローの自動選択（名指しだけ）
- 実行中の作業ツリーの保護（ロック）。対話側が実行中に同じリポジトリを編集しないことは、スキルの手順で守る
- MCP サーバー

### Claude Code 側のスキル

対話中の Claude が呼び出し方を迷わないよう、スキル（仮称 `vuoi-handoff`）にまとめる。

1. 対話の内容からブリーフを書く（目的、決定済みの方針、受け入れ条件、触らない範囲、参考にしたファイル）。決定済みの方針は「決定事項」と明記し、ワークフロー側で設計し直させない
2. ブリーフをユーザーに見せて確認を取る
3. `vuoi exec <name> --brief <file> --json <file>` をバックグラウンドで起動する。実行中はそのリポジトリのファイルを編集しない
4. 終了したら結果の JSON を読み、要約・blocked の理由・変更されたファイル・副次タスクを報告し、次の一手（差分のレビュー、コミット、PR 作成、追加指示での再実行）を提案する

## 決定事項（2026-11-19）

- 既存の `vuoi workflow run` は拡張せず、新しいコマンドを作る
- 開始前から未コミットの変更がある場合、`has_changes` は常に「変更あり」とする（上記のとおり許容する）
