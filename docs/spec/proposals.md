# 副次タスクの起票（Proposals）

## 位置づけ

作業中に発見した範囲外の問題を、新しいチケット（proposal）として起票する機能です。独立したノードにはせず、既存ノードの副産物として収集します。

| 収集元 | 内容 |
|---|---|
| 計画 | 実装の前提として先に必要なもの |
| 実装 | 作業中に踏んだ、無関係な不具合 |
| レビュー | 受け入れ基準に紐づかない所見 |
| ゲート | flaky テストの検出 |

**本来の目的はタスクを増やすことではなく、実装ノードが範囲外のバグをその場で直すのを止めることです。** 各ノードには「範囲外の問題を見つけたら、直さずに proposal に記録して作業を続けること」を指示します。これにより diff が小さくなり、レビューが通りやすくなり、ゲートの失敗も減ります。

## 起票候補が持つ情報

- タイトルと本文
- 根拠（evidence）: 該当箇所の指示（例: `src/foo.py:142`）
- 推奨タグ
- 種別: `bug` / `chore` / `spike` / `debt`

根拠が空、または指すファイルが実在しない候補は、機械的に破棄します。

## 暴走の防止

エージェントが起票し、ポーラーが起票されたものを拾う構造は正のフィードバックを持ちます。次の3つの歯止めを必ず入れます。

1. **起票先は Inbox（Ready ではない）。** 自動生成カードは自動では拾われません。人間が目を通して Ready に上げたものだけが実行されます。これでループが構造的に切れます。
2. **世代深度の制限。** 深度 2 以上のタスク（自動起票の自動起票）からは起票させません。
3. **1ランあたりの上限（3件）。** 超過分は破棄し、代わりに「N 件の問題を検出」という要約カードを1枚作ります。大量起票は起票の問題ではなく実装対象の問題なので、そちらを人間が見るべきです。

## 重複排除

起票前にタスクソースのネイティブ検索で類似チケットを探します。見つかった場合は起票せず、既存チケットへ「再発を確認した」旨をコメントします。タイトルの類似で十分です。

## 冪等性

起票は冪等に動作します。各候補には一意な ID を持たせ、チケットの説明文にその ID を埋め込みます。再開時はこの ID で検索してから作成するため、タスクソース側に冪等性キーが無くても二重起票は起きません。

## 起票のタイミング

**終端状態に関わらず、ラン終了時に必ず起票します。** ゲートが落ちたランでも、途中で踏んだ無関係なバグは実在するためです（根拠は既存コードを指すため、そのランの成否と独立です）。

例外は `abandoned` で、この場合は親チケットへのリンクを外し、プロジェクトのみ紐付けて作成します。
