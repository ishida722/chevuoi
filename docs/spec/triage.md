# プロジェクト割り当てと triage

## プロジェクト割り当て（決定的）

チケットのタグから対象プロジェクトを決定します。タグとプロジェクトの対応表は静的な設定として持ちます（例: `MIRAI` → `mirai`、`SSC101` → `ssc101`）。

各プロジェクトは次の情報を持ちます。

- 対象リポジトリと基点ブランチ
- ゲートで実行するコマンド（テスト・lint・型チェック）
- worktree の作成先
- PR テンプレート（任意）

割り当ての規則は次のとおりです。

- タグが対応表で引けない場合 → `needs_human`（理由: `unmapped_tag`）で即終了
- 複数のプロジェクトにヒットした場合 → 同様に `needs_human`

**LLM に推測させません。** 誤ったリポジトリで実装ランを1本溶かすコストのほうが、人間がタグを1つ付けるコストより遥かに高いためです。

## triage（経路の選択）

triage は入口で1回だけ行います。3層で判断し、上位の層で決まれば下位の層は実行しません。

### 第1層 — 決定的な事前チェック（LLM 不使用）

タグとタイトルの規則で経路を決めます。

| 条件 | 結果 |
|---|---|
| `spike` タグがある | `investigate` 経路 |
| `adr` タグがある | `design` 経路 |
| タイトルが `typo` / `bump` / `deps` で始まる | `trivial` 経路 |
| 本文が空 | `needs_human` へ |
| 上記いずれにも該当しない | 第2層へ |

人間がラベルを1つ付ける行為自体がルーティング決定です。最も安く最も正確な判断手段として、これを優先します。

### 第2層 — LLM による分類（第1層で決まらなかったものだけ）

チケット内容とリポジトリの読み取りのみを許可した `claude -p` に、次の情報を返させます。

- 経路の候補（1つ）
- 確信度（high / それ以外）
- 判断理由
- 対象ファイルの候補
- 受け入れ基準の一覧（ID つき）

判断の実質は「**受け入れ基準を書き下せたか**」「**対象ファイルを特定できたか**」の2点です。抽象的な種別分類より、この2点のほうが安定します。

### 第3層 — 棄権パス（必須）

確信度が high でない、または受け入れ基準が1件も抽出できなかった場合は、`needs_human`（理由: `ambiguous_ticket`）で終了します。

必ずどれかを選ばされるルーターは必ず間違えます。誤ルーティングのコストは実行1本ぶんに及ぶため、棄権パスを必ず用意します。

## 経路の途中での reroute

計画ノードが「これは実装ではなく調査だ」と気づく場合があります。このための reroute（経路の変更）を、**1ランにつき1回まで**許可します。

- reroute すると、新しい経路の先頭から実行し直す
- 2回目の reroute が要求された場合は `needs_human`（理由: `reroute_exhausted`）で終了する

回数を1回に縛ることで、計画と実装の間を往復し続ける状態が構造的に起こらなくなります。
