# 全体フロー

1回の実行（`vuoi run`）は、次の流れで各タスクソースを1巡します。

```
poll (cron/systemd timer)
  └─ for each source:
       チケット取得 ──→ [Task]
         └─ クレーム              … 冪等。失敗したら次のタスクへ
              └─ プロジェクト特定 … タグ→プロジェクト。決定的
                   └─ triage      … 経路を1つ選ぶ。LLM 使用可（棄権あり）
                        └─ 経路の実行 … LLM はノード内でのみ使用
                             │
                             ├─ worktree 準備
                             ├─ 計画      (claude -p)
                             ├─ 実装      (claude -p)   ←──┐
                             ├─ ゲート    (決定的判定)  ───┤
                             └─ レビュー  (claude -p)   ───┘ 所見が残る限り戻る
                             │
                        副次タスクの起票
                        チケットへの結果反映
                        worktree の後始末
```

ゲート・レビューから実装へ戻る後ろ向きの遷移があるため、フローは一直線ではありません。

## 各段階の役割

チケット取得からクレームまで
: タスクソースから実行対象のチケットを取り出し、二重実行を防ぐためにクレーム（占有）します。クレームに失敗したチケットはスキップし、次へ進みます（{doc}`task-sources`）。

プロジェクト特定と triage
: チケットのタグから対象プロジェクトを決定し、チケット内容から経路を1つ選びます。判断がつかない場合は人間へ差し戻します（{doc}`triage`）。

経路の実行
: 選ばれた経路のノード列を順に実行します。試行回数・時間の予算を超えた場合や収束しない場合は、対応する終端状態で打ち切ります（{doc}`routes`、{doc}`gate-review`）。

後処理
: 実行結果に関わらず、収集した副次タスクを起票し、終端状態に応じてチケットを更新し、worktree を後始末します（{doc}`proposals`、{doc}`outcomes`、{doc}`worktree`）。

## 実行中の外部変化への対応

人間が実行中にチケットをアーカイブ・移動する場合があります。高コストな処理の前と結果反映の直前にチケットの有効性を確認し、外れていた場合は `abandoned` として終了します。このときチケットには触らず、worktree のみ掃除します。
