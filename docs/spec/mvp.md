# MVP（v1.0.0）

## 位置づけ

本仕様書の他の章は Che vuoi? の**全体像**を定めるものであり、そのまま最初のリリースの範囲ではありません。この章は、最初のリリースである **v1.0.0（MVP）** の範囲を定めます。

MVP の狙いは、cycle スキル（プロンプトベースの自律開発ループ）を構造化することです。ターンを明確に区切り、統合されたタスク処理をその上に乗せます。解決すべき問題は「チケットを起点に、隔離された作業環境で `claude -p` を1回走らせ、結果をチケットに返す」というループを確実に回すことであり、それ以外の機能は v1.0.0 では作りません。

## MVP のフロー

1回の実行（`vuoi run`）は、次の一直線のフローを Trello の対象カードごとに繰り返します。

```
カード取得（Trello・1リストのみ）
  └─ クレーム（In Progress へ移動）
       └─ プロジェクト分配（タイトルのタグ → プロジェクトフォルダ）
            └─ worktree 構築
                 └─ 処理ノード（claude -p を1回実行）
                      └─ カードをレビュー待ち（In Review）へ移動し、結果をコメント
```

後ろ向きの遷移（リトライループ・レビューループ）はありません。ノードが1つしかないため、フローは常に一直線です。

### 各段階の仕様

カード取得とクレーム
: Trello の Ready 相当リストからカードを取得します。クレームは In Progress 相当リストへの移動で表現し、移動できなかったカードはスキップします。タスクソースは Trello のみで、抽象化レイヤーは設けません。

プロジェクト分配（決定的）
: カードの**タイトルに付記されたタグ**（例: `MIRAI ログイン修正` の `MIRAI`（タイトルをスペースで区切った先頭の1語））を設定の対応表で引き、対象プロジェクトフォルダを決定します。引けない場合はそのカードをスキップし、理由をログに残します。LLM に推測させない原則（{doc}`triage`）は MVP から適用します。

worktree 構築
: 対象プロジェクトのリポジトリに git worktree を作成し、作業を隔離します。ブランチ名をカードの外部 ID から決定的に導出する規則は {doc}`worktree` と同じです。

処理ノード（1ノード）
: worktree 内で `claude -p` を**1回**実行します。計画・実装・レビューの分割、triage、ゲート、レビューループはすべてノード内のプロンプトに委ね、パイプラインとしては1ノードとして扱います。テスト・lint の実行はプロジェクトフォルダ側の規約（CLAUDE.md やプロジェクト内の設定）に従ってノード内で行われるものとし、**vuoi 自体はその内容に関知しません**。

結果反映
: ノードの終了後、カードをレビュー待ち（In Review 相当）リストへ移動し、結果（PR の URL など、ノードの出力）をコメントします。ノードが異常終了した場合も、エラーをコメントした上で In Review 相当リストへ移動します（In Progress に残すと、エラーなのか作業中なのか判別できないため。エラーでも動作が終わったらいったんレビューを要求します）。

## 設定

設定は**タグとプロジェクトフォルダの紐付け**を中心とした最小限にします。

- タグ → プロジェクトフォルダ（リポジトリのパス）の対応表
- Trello の認証情報と対象リスト（Ready / In Progress / In Review 相当の各 ID）
- worktree の作成先

ゲートコマンド・PR テンプレート・予算などのプロジェクト設定（{doc}`triage` 参照）は持ちません。lint・テスト・コーディング規約はプロジェクトフォルダに置かれたものをノードが読む前提です。

## UI

UI は CLI のみです。v1.0.0 で提供するコマンドは次の2つに絞ります。

```bash
vuoi run    # Trello をポーリングして1巡
vuoi gc     # 終端済み worktree の掃除
```

`resume` / `status` は提供しません（実行状態の永続化を伴うため）。常駐は全体仕様（{doc}`cli`）と同じく外部のスーパーバイザ（borro / cron / systemd timer）に任せ、`vuoi run` は1巡で終了します。

## 全体仕様との対応

| 機能 | 全体仕様 | v1.0.0 |
|---|---|---|
| タスクソース | 抽象化＋ Trello / Jira / GitHub Issues | Trello のみ・抽象化なし |
| triage / 経路 | 4経路＋3層 triage（{doc}`triage`、{doc}`routes`） | なし（全カードを単一フローで処理） |
| ノード構成 | 計画・実装・レビュー等に分割 | 1ノード（`claude -p` 1回） |
| ゲート | 決定的ゲート（{doc}`gate-review`） | なし（プロジェクト側の責務） |
| レビューループ | 所見の凍結・収束保証（{doc}`gate-review`） | なし |
| 終端状態 | 6状態＋サブ分類（{doc}`outcomes`） | done / failed の2状態 |
| 副次タスクの起票 | あり（{doc}`proposals`） | なし |
| 再開可能性 | `vuoi resume`（{doc}`cli`） | なし |
| worktree | あり | あり（同じ規則） |
| CLI | run / resume / status / gc | run / gc |

## MVP でも譲らない原則

機能を削っても、次の原則は v1.0.0 から守ります。

1. **フロー制御に LLM を使わない。** プロジェクト分配は対応表、カード移動は決定的なルールで行います。
2. **クレームとカード操作の冪等性。** 二重起動やクラッシュ後の再実行でカードが二重に動きません（{doc}`task-sources`）。
3. **PR の自動マージをしない。** 取り込みは常に人間が行います。
4. **Trello との通信は REST API 直接。** MCP は使いません（{doc}`task-sources`）。

## v1.0.0 以降

MVP で1ノードに詰め込んだ責務を、全体仕様のパイプラインへ段階的に分解していきます。順序の目安は、運用で最初に痛む箇所から、(1) ゲートの外出し（決定的判定）、(2) 終端状態の細分化と `needs_human`、(3) triage と経路の導入、(4) レビューループ、の順を想定します。
