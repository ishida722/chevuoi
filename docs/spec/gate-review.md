# ゲートとレビュー

## ゲート（決定的判定）

ゲートは、プロジェクトが定義するコマンド（テスト・lint・型チェック）を worktree 内で実行し、終了コードだけで合否を決めるノードです。

- **LLM を使いません。** 「テストが通ったか確認して」と LLM に聞くことは仕様違反です
- 実行ログは試行ごとに保存し、失敗時は実装ノードへの入力として渡します
- 実行にはタイムアウト（30 分）を設けます

**ゲートが緑でなければレビューを実行しません。** 赤い diff のレビューはトークンの無駄です。

## レビュー

レビュアー（LLM）は所見を返すだけで、合否（verdict）を返しません。合否は所見の内容から決定的なルールで決めます。

### 所見の形式

各所見は次の情報を持ちます。

- 重大度: `blocker` / `major` / `minor`
- 対象のファイルと行
- 対応する受け入れ基準の ID（無い場合は自動的に `minor` へ降格）
- 指摘内容と、その根拠（evidence）
- 解決済みかどうか

### 合否の判定ルール

- 未解決の `blocker` が1件でもあれば → 差し戻し
- 未解決の `major` が2件以上あれば → 差し戻し
- それ以外 → 合格（`minor` は記録して PR 本文に載せるのみ）

閾値は調整可能なパラメータとして扱います。

### 所見の凍結（収束保証）

ラウンドごとに新しい指摘が出ると、実装が直る速さと同じ速さで基準が動くため、レビューは原理的に収束しません。次の規則で収束を保証します。

- **1周目**: 所見の集合を確定（凍結）する
- **2周目以降**: 凍結した所見を渡し、各所見が解決済みかどうかだけを返させる
- 2周目以降の**新規所見は `blocker` のみ受理**する。それ以外は破棄してログに残す
- 受け入れ基準に紐づかない所見は自動的に `minor` へ降格し、起票候補へ回す（{doc}`proposals`）

### 所見の機械検証（捏造の除去）

次のいずれかに該当する所見は機械的に破棄します。

- 変更していないファイルへの指摘
- 変更していない行への指摘
- 存在しない受け入れ基準 ID への言及

LLM の出力を機械で検算できる数少ない箇所であり、コストはかかりません。

### 発振検知

実装のたびに diff のハッシュを記録し、過去と同一の diff に戻った場合は `oscillation` として即座に打ち切ります。試行回数の上限を待つより早く効きます。

### レビューループの流れ

1. 実装を実行する。入力は計画・未解決の所見・最新のゲート結果のみ
2. ゲートを実行する。失敗なら実装へ戻る（試行上限超過で `failed_gate`）。**失敗時はレビューへ進まない**
3. 発振を検知したら `oscillation` で終了する
4. レビューを実行する。レビュアーが判断不能を申告したら `needs_human`（理由: `reviewer_abstained`）で終了する
5. 所見を機械検証にかけ、通過したものだけを残す
6. 1周目なら所見を凍結し、2周目以降は解決状況を反映する
7. 合否判定が合格なら `done` で終了する
8. 不合格ならラウンドを進める。ラウンド上限に達したら `needs_human`（理由: `review_unconverged`）で終了する

実装へ戻すのは**未解決の所見リストだけ**です。レビュアーの文章全体も、前回の実装の会話も渡しません。
