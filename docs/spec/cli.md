# CLI と運用

## コマンド

```bash
vuoi run                      # 全ソースをポーリングして1巡
vuoi run --source trello --limit 1
vuoi review-requests          # レビュー依頼中の PR をカードとして起票
vuoi review-requests --limit 5
vuoi resume <run_id>          # 中断ランの再開
vuoi status                   # 未終端ランの一覧
vuoi gc --older-than 7d       # 終端済み worktree の掃除
vuoi workflow list            # ユーザー定義ワークフローの一覧（コード実行なし）
vuoi workflow run <name> ["メッセージ"]   # ワークフローを名指しで1回実行
vuoi workflow select <title> ["本文"]    # カード内容からワークフローを選ぶ（ルーター確認）
vuoi card issue <tag> <title>            # Inbox にカードを1枚発行（発行サービスの確認）
vuoi card issue <tag> <title> --body "本文" --kind bug
```

`workflow run` は最後に追加されたメッセージ本文を標準出力に出します。メッセージを増やさないワークフローの場合は、`messages` を除いた最終 state を表示します。失敗（存在しない・無効・ロード失敗）は標準エラーに理由を出して終了コード 1 で終わります。`workflow select` はルーターのモデル・選択結果・確信度・理由を表示し、棄権した場合は終了コード 2 で終わります。

`review-requests` は自分にレビューが依頼されている open な PR を取得し、Inbox にカードを起票します（詳細は {doc}`task-sources` の「PR レビュー依頼の取り込み」）。起票結果を標準出力に一覧し、起票できなかった PR があれば理由を標準エラーに出して終了コード 1 で終わります。`--limit`（既定 20）で 1 回に見る PR の件数を決め、上限に達した場合は古い依頼が残っている旨を警告します。`run` と同じく定期実行を想定したコマンドです。

`card issue` は発行サービスを単体で確かめるコマンドで、Inbox にカードを1枚だけ作ります（{doc}`proposals`）。親カードを持たない起票なので、世代は 0 になります。タグは空白を含まない1語で指定し、カードのタイトル先頭に前置します。`--kind` は `bug` / `chore` / `spike` / `debt` から選び、既定は `chore` です。

起票は冪等で、冪等キーはタイトルだけから決まります（大文字小文字と空白の差は無視します）。同じタイトルで2回実行しても2枚目は作らず、既存のカードの URL を返します。タグや本文だけを変えた場合も同じです。ただし照合先は Inbox の中だけなので、1枚目を Inbox の外へ動かしたあとに同じタイトルで実行すると、2枚目ができます。結果は発行か既存かの別と URL を標準出力に出します。タグの形式が不正な場合と、起票に失敗した場合（Inbox 未設定・API エラー）は、理由を標準エラーに出して終了コード 1 で終わります。

## 未登録タグの扱い

タグとプロジェクトの対応表（{doc}`triage`）で引けないタグを `vuoi card issue` に渡した場合は、警告を標準エラーに出したうえで起票を続けます。終了コードは 0 です。タグはそのままタイトルに前置し、対象プロジェクトは特定しないままカードを作ります。あとから対応表にタグを足せば、そのカードは通常どおり処理できます。

同じ「引けないタグ」でも、Ready のカードを処理する側は `needs_human`（理由: `unmapped_tag`）で即終了します（{doc}`triage`、{doc}`outcomes`）。入口ごとに挙動を分けるのは、間違えたときのコストが違うためです。処理側が誤ったリポジトリへ進むと実行を1本まるごと溶かしますが、起票側でタグを取り違えても Inbox のカード1枚で済み、それを Ready へ上げるかどうかは人間が決めます（{doc}`proposals`）。

```{note}
続行と停止のどちらを採るかは仕様として決めていませんでした。先に実装した挙動（続行）をここで追認します。停止へ倒す判断をした場合は、この節と実装をあわせて直します。

警告の出力は未実装です。現在の実装は対応表を参照せず、引けないタグでも何も言わずに起票します。
```

## 再開可能性

実行状態は遷移のたびに永続化し、プロセスが落ちても `vuoi resume` で続きから再開できます。外部への作用（カード移動・起票など）はすべて冪等であり、再開時のリプレイで正しい状態に収束します。

## 常駐方法

常駐は systemd timer + oneshot service で行います。`claude -p` はデーモンではなく、1回の呼び出しで1ターン走って終了するため、ターン・クラッシュ・再起動をまたぐ継続にはスーパーバイザが必要です。

- `RuntimeMaxSec` でハードストップをかける
- `Restart=no` とする
- ログは journald に出す

## 計測する指標

運用の改善判断のため、次の指標を記録します。

| 指標 | 用途 |
|---|---|
| 経路 × 終端状態の混同行列 | triage の精度。誤ルーティング1件のコストは実行1本ぶんなので、改善 ROI が最も高い |
| レビューのラウンド数分布 | 1周通過率。9割なら閾値が緩く、3割なら厳しい |
| 所見の生存率 | 機械検証で破棄された割合。高ければレビューのプロンプトが悪い |
| 起票の採用率 | 自動起票のうち人間が Ready に上げた割合。3割未満なら起票基準が緩すぎる |
| 実装の diff 行数 | 起票機能がスコープ規律として効いているかの副次指標 |
